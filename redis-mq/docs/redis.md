## 1. 历史背景

### 1.1 诞生

Redis 由 **Salvatore Sanfilippo**(网名 **antirez**)于 2009 年开发。

背景:他在做一个实时 Web 统计系统(LLOOGG)时,发现 MySQL 扛不住高并发实时读写,
于是写了一个**基于内存的数据结构服务器**,把数据放在内存、用简单的协议读写。名字
**REmote DIctionary Server**(远程字典服务器)点明了它的本质:一个远程的、按 key
组织的数据结构集合。

### 1.2 演进时间线

| 时间 | 事件 |
|------|------|
| 2009 | antirez 发布首个版本 |
| 2013 | Redis 2.8 引入哨兵(Sentinel)、`SCAN` 等 |
| 2015 | Redis 3.0 发布集群(Cluster) |
| 2018 | Redis 5.0 引入 Streams 数据结构 |
| 2020 | Redis 6.0 引入 ACL、多线程 IO、RESP3 |
| 2022 | Redis 7.0 引入 Functions |
| 2024 | 许可从 BSD 改为 RSALv2 / SSPLv1,引发社区争议(催生 Valkey 分支) |

### 1.3 设计理念

- **内存优先**:数据驻留内存,读写微秒级;持久化是"可选附加",而非主路径。
- **单线程执行命令**(6.0 前):避免锁竞争、简单可预测;6.0+ 只把**网络 IO** 多线程化,
  **命令执行仍单线程**,所以单个慢命令仍会阻塞。
- **丰富数据结构**:String / Hash / List / Set / ZSet / Stream / Bitmap /
  HyperLogLog / Geo 等,每种结构对应一类典型问题。

## 2. 常用使用场景

| 场景 | 常用数据结构 | 说明 |
|------|--------------|------|
| **缓存** | String / Hash | 热点数据缓存,扛住读流量、减轻 DB 压力 |
| **分布式锁** | String(`SET NX`) | 跨进程互斥,见本仓库 `lock_service.py` |
| **计数器 / 限流** | String(`INCR`) | 原子自增,配合 `EXPIRE` 做窗口限流 |
| **排行榜** | ZSet | score 排名,见本仓库 `score_rank.py` |
| **会话存储** | String / Hash | 用户 session 集中管理、多实例共享 |
| **消息队列** | List / Stream | 轻量队列(持久化与吞吐弱于 Kafka) |
| **去重 / 存在性** | Set / 布隆过滤器 | 唯一性判断、已读集合 |
| **签到 / 位图** | Bitmap | 按位存状态,极省内存 |

### 什么时候不适合 Redis

- **大数据量冷数据**:内存昂贵,应落盘到 DB / 数仓。
- **强持久化 / 严格不丢**:Redis 持久化是异步的,Kafka 或数据库更合适。
- **复杂查询 / 关联 / 事务**:数据模型是 key-value,应回关系型 / 文档型 DB。
- **需要精确一次的消息**:Redis 队列默认 at-least-once,Stream 的 ack 机制也较粗糙。

## 3. 分布式场景下的关注点

### 3.1 持久化

| 方式 | 原理 | 特点 |
|------|------|------|
| **RDB** | 定期快照到二进制文件 | 恢复快、体积小,但可能丢最近一次快照后的数据 |
| **AOF** | 追加记录每条写命令 | 可配置 `fsync`(always / everysec / no),丢数据少,但文件大、恢复慢 |
| **混合**(4.0+) | RDB 全量 + AOF 增量 | 兼顾两者 |

### 3.2 主从复制

- **主写从读**,可做读写分离。
- 复制是**异步**的:主宕机时,从可能还没收到最近写入,存在数据丢失窗口。

### 3.3 高可用:哨兵(Sentinel)

- 监控主从健康,**主宕机自动选新主**并切换客户端连接。
- 解决"单主故障",但**不做分片**——写仍然压在单主上。

### 3.4 分片:集群(Cluster)

- 把 16384 个 **slot** 分配到不同节点;key 按 `CRC16(key) % 16384` 落到某个 slot,
  从而路由到对应节点,实现水平扩展。
- **hash tag**(如 `{user}:xxx` 与 `{user}:yyy`)只对 `{}` 内部分取模,把相关 key 固定
  到同一 slot,支持跨 key 操作。
- 集群下**单条命令只作用于一个 key**;多 key 操作要求同 slot,或用 Lua / 事务。

### 3.5 内存与过期

- `maxmemory` 设上限,配合**淘汰策略**:`noeviction`(满则拒写)、`allkeys-lru` /
  `allkeys-lfu`(整体淘汰)、`volatile-lru` / `volatile-lfu`(只淘汰带 TTL 的)。
- **过期策略**是"惰性删除 + 定期扫描"结合:访问到过期 key 才删 + 后台定时抽检,
  所以过期 key 不会立即消失,统计大小时可能偏高。

### 3.6 缓存一致性

- 经典 **Cache Aside**:读未命中回源并写缓存;写时**先更新 DB 再删缓存**(或延迟双删),
  避免"删缓存→还没更新 DB→别的请求又把旧值写回缓存"的竞态。
- 本质是**最终一致**;要强一致就别用缓存(或引入版本号 / 分布式事务)。

### 3.7 缓存穿透 / 击穿 / 雪崩

| 问题 | 现象 | 对策 |
|------|------|------|
| **穿透** | 查不存在的 key,每次都打到 DB | 布隆过滤器 / 空值缓存 |
| **击穿** | 热点 key 过期瞬间大量请求打到 DB | 互斥锁重建 / 逻辑过期 |
| **雪崩** | 大量 key 同时过期,DB 瞬间被打垮 | 过期时间加随机抖动 / 多级缓存 |

### 3.8 单线程与性能陷阱

- 单线程执行命令,天然无锁;但 **O(N) 大命令会阻塞**整个实例——`KEYS`、`SMEMBERS`、
  大范围 `ZRANGE` 都是雷区,生产用 `SCAN` 族替代 `KEYS`。
- **big key**:单个 key 过大(大 hash / 大 set)会让删除、过期、复制都变慢,应拆分或改结构。

### 3.9 与 Kafka 的定位差异

| 维度 | Redis | Kafka |
|------|-------|-------|
| 定位 | 内存缓存 / 数据结构 | 持久化消息 / 事件流 |
| 单条延迟 | 微秒级 | 毫秒级 |
| 持久化 | 可选(RDB / AOF) | 落盘、可回放 |
| 吞吐 | 高,但受单机内存与单线程限制 | 极高,水平扩展 |
| 典型场景 | 缓存 / 锁 / 排行榜 / 计数 / 会话 | 日志 / 事件 / 管道 / 削峰 |

> 一句话:Redis 是"快但易失的结构化内存",Kafka 是"慢一点但持久可回放的日志流",
> 二者互补,常在同一系统里各司其职。

---

## 小结

- **历史**:antirez 为实时统计性能而生,核心是"内存 + 丰富数据结构",已演进到
  主从 / 哨兵 / 集群 + 多线程 IO。
- **场景**:缓存、锁、计数、排行榜、会话、轻量队列、去重、位图——凡"快 + 数据结构"
  皆可。
- **分布式关注点**:持久化(RDB/AOF)、主从复制、哨兵高可用、Cluster 分片、内存淘汰
  与过期、缓存一致性、穿透/击穿/雪崩、单线程大命令陷阱。这些是生产环境真正要
  下功夫的地方。
